## 1. هدف و تصمیم پایه

هدف، طراحی، پیاده‌سازی و مهاجرت به سامانه‌ای کاملاً وب و PWA برای فروش و پخش مویرگی است؛ با پایگاه داده جدید و مستقل. نسخه دسکتاپ ShirinNovin فقط منبع مهاجرت خواهد بود و پس از Cutover بازنشسته می‌شود.

تصمیم‌های غیرقابل نقض در سند مبنا:
- محصول نهایی مرورگر + PWA است؛ هیچ WinForms، Wrapper، Electron یا مؤلفه دسکتاپ در محصول هدف وجود ندارد.
- مهاجرت یک‌طرفه است؛ Dual-Run و همگام‌سازی دوطرفه در دامنه نیست.
- سامانه هدف در زمان اجرا به NGT/FRU/API قدیم، احراز هویت قدیم، Linked Server یا Crystal Reports runtime وابسته نمی‌شود.
- Print Service محلی فقط برای تجهیزات و چاپ است؛ منطق کسب‌وکار و دسترسی مستقیم به DB ندارد.
- داده‌های تاریخی و قواعد مالی باید قابل ردیابی، قابل آزمون و مورد تأیید مالکان کسب‌وکار باشند.

## 3. معماری هدف و مرزها

**معماری توصیه‌شده در سند مرجع:** Modular Monolith روی ASP.NET Core؛ React + TypeScript + Next.js (یا SPA مبتنی بر Vite) به‌صورت PWA؛ SQL Server مستقل با اسکیماهای دامنه؛ Identity + OpenIddict/OIDC؛ RBAC + DataScope؛ Outbox + Worker؛ Read Model گزارش؛ On-Premise.

اصول طراحی:
- API-first و قراردادهای نسخه‌پذیر؛ UI فقط مصرف‌کننده API.
- کلید منطقی مستقل همراه با LegacyId/LegacyNo برای ردیابی مهاجرت.
- تاریخ ذخیره‌شده به شکل Gregorian/UTC و نمایش شمسی/Asia-Tehran.
- decimal دقیق برای مبلغ/قیمت/مقدار؛ بدون float و بدون گردکردن عمومیِ تأییدنشده.
- Snapshot اسناد تأییدشده؛ تغییر اطلاعات جاری کالا/مشتری نباید واقعیت سند گذشته را بازنویسی کند.
- RBAC و DataScope در مرز API/Query/Service؛ نه صرفاً مخفی‌سازی UI.
- Idempotency، Outbox، retry کنترل‌شده، audit، concurrency و رسیدگی به failure جزئی.
- گزارش‌گیری از Read Model؛ حذف Crystal runtime.
- PWA آفلاین با Service Worker، IndexedDB، Outbox محلی و sync delta.
- فایل‌ها در Object Storage یا file server امن؛ URL امضاشده و کنترل نوع/حجم.
- بدون Trigger یا Stored Procedure برای قواعد اصلی کسب‌وکار؛ استفاده محدود و مستند برای عملیات داده/گزارش مجاز طبق طراحی.

### تصمیم‌های فناوری که باید قبل از اجرا تثبیت شوند
D1 محل DB (توصیه سند: سرور جدا)؛ D2 دامنه تاریخ مهاجرت؛ D3 موتور گزارش؛ D4 On-Premise یا Private Cloud؛ D5 پایلوت یک مرکز یا همه مراکز؛ D6 سطح تاریخچه CRM؛ D7 GL سبک داخلی یا اتصال حسابداری؛ D8 ورود B2B به MVP یا فاز بعد.

## 4. دامنه محصول و جریان‌های انتها‌به‌انتها

دامنه‌های اصلی: سازمان و داده پایه، مشتری/اعتبار/قلمرو، کالا، قیمت و تخفیف، سفارش و فاکتور، مرجوعی، انبار و خرید، توزیع و ناوگان، ونسل و کال‌سنتر، POS وب، خزانه/چک/وصول، حسابداری، هدف و پورسانت، CRM/ویزیت، گزارش، امنیت، تنظیمات و یکپارچه‌سازی/مودیان.

جریان‌های پذیرش اجباری:
1. **Order-to-Cash:** مشتری و اعتبار → قیمت/تخفیف → سفارش → تأیید → رزرو → برداشت/بارگیری → تحویل → فاکتور → وصول/تسویه → حسابداری و گزارش.
2. **Procure-to-Stock:** تأمین‌کننده → سفارش خرید → دریافت/بازرسی → بچ/انقضا → انبارش → بدهی و پرداخت → تطبیق موجودی.
3. **Return-to-Resolution:** درخواست/مجوز → دریافت و بازرسی → انبار سالم/قرنطینه/اسقاط → بستانکار/جایگزینی/بازپرداخت → حسابداری.
4. **Route-to-Delivery:** برنامه ویزیت → مسیر/خودرو → بارگیری → اجرا و GPS → اثبات تحویل یا علت عدم تحویل → وصول و تسویه.
5. **Promotion-to-Settlement:** کمپین → شرایط و قیمت → تأیید → اجرا → تسویه و تحلیل اثربخشی.
6. **Period Close:** تطبیق زیرسیستم‌ها → کنترل اسناد → بستن دوره → صورت‌های مالی و ردپای ممیزی.

## 6. مهاجرت، تطبیق و Cutover

- ETL به Staging؛ اجرای تکرارپذیر و idempotent؛ نگهداری LegacyId/LegacyNo و گزارش خطا.
- مهاجرت موجی بر اساس وابستگی: سازمان/کاربران و داده مرجع → مشتری/کالا → قیمت/تخفیف → سفارش/فاکتور/مرجوعی → انبار/پرداخت/چک/مانده → تور/ویزیت و تنظیمات موردنیاز.
- هر تبدیل، پاکسازی یا استثنا باید در Data Dictionary و Migration Mapping ثبت شود؛ داده نامطمئن حذف نشود.
- تطبیق چندسطحی: شمار رکورد، جمع مبلغ، جمع مقدار، مانده مشتری، موجودی به تفکیک انبار/کالا/بچ، شماره اسناد و نمونه‌گیری جزئی.
- سه Dry-Run با گزارش اختلاف و رفع ریشه‌ای؛ نه صرفاً اصلاح دستی خروجی.
- در Cutover، توقف نوشتن در سامانه قدیم، Snapshot نهایی، اجرای بارگذاری نهایی، تطبیق، Go/No-Go و سپس انتقال کاربران.
- Rollback باید علاوه بر Backup، تکلیف تراکنش‌هایی را که پس از Cutover در سامانه جدید ثبت شده‌اند روشن کند؛ بازگشت ساده به Backup به‌تنهایی کافی نیست. روش بازگشت/بازیابی و جلوگیری از تکرار سند باید پیش از Go-Live تمرین و تصویب شود.
- پس از Cutover، سامانه قدیم فقط Read-only/Archive و سپس طبق چک‌لیست امنیتی و قانونی بازنشسته شود.

## 7. دروازه‌های پذیرش

- **G0 Ready to Migrate:** نگاشت، ابزار، محیط و مسئولیت‌ها آماده.
- **G1 Data Quality:** استثناها، مالک داده و قواعد پاکسازی تأیید شده.
- **G2 Reconciliation:** تطبیق عددی/مالی/موجودی در آستانه‌های مصوب؛ اختلاف حل‌نشده = توقف.
- **G3 UAT:** سناریوهای نقش‌محور و جریان‌های اصلی تأیید.
- **G4 Security:** Threat Model، MFA نقش‌های حساس، Least Privilege، آزمون امنیت و رفع یافته‌های بحرانی.
- **G5 Operations:** Backup/Restore، مانیتورینگ، Runbook، ظرفیت و پشتیبانی آماده.
- **G6 Go/No-Go:** امضای مالک کسب‌وکار، فناوری، مالی و عملیات.
- **G7 Final Acceptance:** تثبیت، انتقال دانش و پذیرش نهایی.

هیچ Cutover بدون عبور مستند از G0 تا G6 مجاز نیست.

## 12. انطباق با مخزن Green-DMS — تصمیم باز، نه تغییر ضمنی

در زمان ثبت این سند، README مخزن Green-DMS معماری فعال را NestJS/TypeScript، PostgreSQL/PostGIS، Next.js و Android اعلام می‌کند؛ سند منبع حاضر ASP.NET Core و SQL Server مستقل را پیشنهاد می‌دهد. بنابراین این دو معماری **هم‌ارز یا قابل ادغام خودکار نیستند**.

این roadmap صرفاً مستندات و برنامه منبع ShirinNovin را ثبت می‌کند و به‌تنهایی مجوز موارد زیر نیست:
- بازنویسی Green-DMS یا تغییر Stack/Database؛
- ایجاد DB جدید یا اجرای مهاجرت روی داده واقعی؛
- Dual-Run، اتصال Runtime به سامانه قدیم یا Cutover؛
- Merge، Deploy یا تغییر محیط عملیاتی.

پیش از تبدیل این roadmap به برنامه اجرایی داخل Green-DMS، مالک باید تصمیم معماری/محصول را ثبت کند: (الف) این سند برنامه محصول جداگانه است؛ (ب) محصول Green-DMS باید با معماری فعلی ادامه دهد و سند به آن نگاشت شود؛ یا (ج) تغییر Stack به‌عنوان تصمیم رسمی، با برآورد، ADR، برنامه انتقال و مجوز مستقل بررسی شود.
