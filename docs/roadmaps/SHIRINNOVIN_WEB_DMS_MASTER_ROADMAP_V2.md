# بخش اول — مبنا، هدف و محدوده

## 0. خلاصه مدیریتی و تصمیم محصول

هدف، ساخت سامانه‌ای مستقل برای فروش و پخش مویرگی است که به‌طور کامل در مرورگر و به‌صورت PWA روی موبایل و تبلت اجرا شود، پایگاه داده جدید داشته باشد و داده‌های موردنیاز را یک‌طرفه از ShirinNovin دریافت کند. نسخه دسکتاپ فعلی فقط منبع استخراج و مهاجرت است و پس از Cutover بازنشسته خواهد شد.

### تصمیم‌های پایه و الزامی
1. محصول هدف Web + PWA است؛ هیچ نسخه WinForms، Wrapper، Electron یا مؤلفه دسکتاپِ کسب‌وکار در محصول هدف ساخته نمی‌شود.
2. پایگاه داده هدف مستقل است؛ در زمان اجرا هیچ Query، Linked Server یا وابستگی عملیاتی به پایگاه داده قدیم وجود ندارد.
3. مهاجرت یک‌طرفه است؛ Dual-Run و Sync دوطرفه جزو راه‌حل نیست.
4. APIهای NGT/FRU، احراز هویت قدیم، مدل دسترسی قدیم و Crystal Reports runtime بازاستفاده زمان اجرا نمی‌شوند.
5. Print Service محلی فقط واسط چاپ و تجهیزات است؛ منطق کسب‌وکار، احراز هویت مستقل و دسترسی مستقیم به DB ندارد.
6. قواعد قیمت، تخفیف، اعتبار، موجودی، وصول و اسناد مالی باید قبل از جایگزینی با داده طلایی و تأیید مالک کسب‌وکار تثبیت شوند.
7. مهاجرت فقط پس از سه Dry-Run، تطبیق کامل، UAT، آزمون امنیت و تصویب رسمی Go/No-Go انجام می‌شود.

## 1. مبنا، منابع، محدودیت‌ها و مفروضات

### 1.1 منابع تحلیل‌شده

- کد منبع برنامه‌های قدیم در دسترس تحلیل نبوده؛ بخشی از رفتار از متادیتا، رویه‌ها و داده استنباط شده و باید با مالک کسب‌وکار تأیید شود.

- ممکن است بعضی جداول/ماژول‌ها در نصب واقعی استفاده نشوند؛ Data Owner باید استفاده یا عدم استفاده را تأیید کند.
- Snapshotها با ادامه فعالیت سامانه قدیم تغییر می‌کنند؛ Snapshot زمان Cutover مرجع نهایی است.

### 1.3 مفروضات

### 1.4 غیراهداف

- نگهداری Crystal runtime، DevExpress یا Janus در سامانه هدف.

### 2.3 قواعد و استثناهای حیاتی
1. `AccYear` در تراکنش‌ها سال شمسی 1402 تا 1405 است؛ شناسه‌های جدول مرجع سال 1،2،5،6 هستند. این دو مفهوم نباید اشتباه گرفته شوند.
2. `SaleNo/OrderNo` در سطح `(AccYear, DCRef)` یکتا هستند. تکرار در سطح سال، به‌علت چندمرکزی بودن، الزاماً Duplicate نیست.
3. 6,947 فاکتور فاقد SaleNo است؛ 120 مورد فعال‌اند. شماره‌گذاری جدید باید بر اساس سال/مرکز انجام شود و LegacyNo/LegacyId حفظ شود.
4. فرمول مبنای فاکتور:  
   `TotalAmount = SUM(Line.Amount) - (Dis1+Dis2+Dis3+OtherDiscount) + (Add1+Add2+OtherAddition) + Tax + Charge`.  
   310 مورد اختلاف باید علت‌یابی و در رجیستر استثنا ثبت شوند؛ اصلاح خاموش داده ممنوع است.
5. 13 فاکتور TotalAmount<=0 (9 فعال) باید از نظر نوع سند، ابطال، اصلاح یا خطای داده تعیین تکلیف شوند.
6. 92 مشتری بدون رکورد مانده‌اند؛ سیاست مانده صفر یا محاسبه از تراکنش‌ها باید توسط مالی تصویب شود.
7. دو انبار بدون ردیف موجودی‌اند؛ خالی بودن موجودی با نبودن رکورد موجودی یکسان نیست.
8. چک‌ها با IsReconciled=0 هستند؛ معنی فلگ، وضعیت وصول، برگشت، سررسید و مانده واقعی باید با مالک مالی تأیید شود.
9. قیمت و تخفیف چندبعدی‌اند؛ قواعد به‌سادگی به یک درصد تخفیف یا یک قیمت کالا تقلیل داده نشوند.

### 2.4 داده‌هایی که منتقل نمی‌شوند
رمزهای قدیمی، هش رمز، Sessionها، توکن‌ها و مدل دسترسی قدیمی مستقیماً منتقل نمی‌شوند. اشیای فنی، گزارش‌های تکراری، داده‌های بلااستفاده و تنظیمات وابسته به دسکتاپ نیز بدون تأیید مالک وارد مدل جدید نمی‌شوند.

## 3. اصول و تصمیم‌های معماری (ADR)

### 3.1 گزینه‌های بررسی‌شده
- توسعه روی سامانه قدیم: زمان اولیه کوتاه‌تر، اما وابستگی، بدهی فنی/امنیتی و ناسازگاری با حذف دسکتاپ را حفظ می‌کند.
- بازنویسی مستقل وب با DB جدید: کنترل کامل، استقلال و نگهداشت‌پذیری؛ مهاجرت و پذیرش دقیق لازم دارد.
- راهکار تلفیقی: ریسک وابستگی زمان اجرا و هم‌زمانی را افزایش می‌دهد.

**توصیه سند مرجع:** بازنویسی مستقل Web + DB جدید با مهاجرت یک‌طرفه.

### 3.3 اصول طراحی
- DDD سبک، Aggregateهای روشن، CQS منطقی، تراکنش کوتاه و RowVersion.
- قواعد قیمت، تخفیف، اعتبار، پورسانت و تخصیص در Domain Service قابل تست.
- API-first؛ UI صرفاً مصرف‌کننده قرارداد API.
- Idempotency برای عملیات مالی و Outbox برای رویدادها، Retry و Dead-letter.
- Soft Delete برای موجودیت‌های کسب‌وکار؛ Audit برای تغییرات حساس.
- عدم استفاده از Trigger برای منطق کسب‌وکار؛ عدم انتقال قواعد اصلی به Stored Procedure.
- Feature Flag برای انتشار کنترل‌شده و ADR/Data Dictionary برای تصمیم‌ها.

## 4. معماری منطقی و اجزای فنی

### 4.1 نمای منطقی
کاربر مرورگر/PWA ← API/BFF و OIDC ← Application Core و Domain Services ← SQL Server مستقل. در کنار آن Read Model/Reporting، Outbox/Workers، Redis Cache، Object Storage، SignalR و Print Service محلی قرار می‌گیرند.

### 4.2 اجزا و مسئولیت‌ها
1. **Web/PWA:** RTL، واکنش‌گرا، فرم‌های سریع، جدول‌های حجیم، داشبورد، جست‌وجوی سراسری، اعلان و آفلاین میدانی.
2. **API/BFF:** احراز هویت، مجوز، اعتبارسنجی، Rate Limit، تجمیع داده، OpenAPI، نسخه‌بندی و Idempotency.
3. **Application Core:** ماژول‌های Sales، Distribution، Inventory، Finance، CRM، Target و Admin.
4. **Domain Services:** Pricing، Discount، Credit، Commission، Allocation، Stock، Tour و Visit.
5. **Data Access:** EF Core برای عملیات نوشتن/موجودیت؛ Dapper برای Queryهای سنگین؛ Migration نسخه‌دار و Seed مرجع.
6. **Workers:** گزارش، پیامک/ایمیل، همگام‌سازی PWA، مؤدیان، پورسانت، بستن روز، پاکسازی و Backfill.
7. **Realtime:** SignalR برای وضعیت تور، داشبورد توزیع، اعلان و تأیید سفارش.
8. **Reporting:** Read Model و Reporting DB/Replica؛ خروجی PDF/Excel/CSV.
9. **Integration:** مؤدیان، پیامک، بانک/چک، POS، GPS، حسابداری و Excel.
10. **Security/Admin:** کاربر، نقش، مجوز، Device/Session، Audit، تنظیمات و Feature Flag.
11. **Print Service:** فقط چاپ/تجهیزات، با API محلی محدود و احراز هویت اختصاصی.

### 4.3 Frontend
- ساختار feature/domain-based؛ کامپوننت‌های مشترک برای فرم، جدول، فیلتر، انتخابگر مشتری/کالا و اسناد.
- RTL واقعی، فونت فارسی خوانا، ارقام و تقویم قابل تنظیم، پشتیبانی متن فارسی/لاتین.
- فرم‌های سریع برای ثبت سفارش، فاکتور، وصول، بارگیری و ویزیت؛ اعتبارسنجی سمت کلاینت و سرور.
- مدیریت State تفکیک‌شده برای Server State، فرم‌ها و Offline Queue.
- Service Worker فقط Cacheهای مجاز؛ داده حساس/مالی بدون سیاست امنیتی صریح در Cache عمومی ذخیره نشود.
- IndexedDB با رمزگذاری/حداقل‌سازی داده محلی، انقضای محلی، قفل دستگاه و پاک‌سازی پس از خروج/لغو دسترسی.
- Sync: Pull تغییرات با `GET /sync/changes?since=...&deviceId=...`؛ Push با `POST /sync/batch` و Idempotency Key؛ پاسخ Accepted/Rejected/Conflict؛ Retry نمایی و حل تعارض ثبت‌شده.

### 4.4 Backend و داده
- ماژولار مونولیت؛ مرزهای دامنه و وابستگی یک‌طرفه.
- اعتبارسنجی ورودی، سیاست مجوز، تراکنش و رویداد Outbox در Application Layer.
- EF Core و Dapper با قراردادهای دسترسی و Queryهای قابل پایش.
- SQL Server جدید با اسکیماهای core، sales، inventory، finance، crm، security، platform و rpt.
- ایندکس متناسب با فیلترهای مرکز/سال/مشتری/کالا/وضعیت؛ بررسی Query Plan؛ Partitioning فقط در صورت اثبات نیاز.
- گزارش‌های سنگین از مسیر Read Model؛ نه Query تحلیلی سنگین روی OLTP.
- فایل‌ها خارج از Webroot و DB، با Hash، MIME واقعی، اسکن و دسترسی کنترل‌شده.

### 4.5 استقرار و ظرفیت
- پیشنهاد On-Premise: دو Node اپلیکیشن، SQL Server جدا، Redis، ذخیره‌سازی فایل و Backup رمزنگاری‌شده؛ توپولوژی نهایی با Sizing و آزمون بار تعیین شود.
- محیط‌های Dev/Test/UAT/Stage/Production جدا و داده غیرواقعی/ناشناس‌سازی‌شده در غیرProduction.
- TLS، مدیریت Secret، CI/CD، Health Check، مانیتورینگ و هشدار.
- مقیاس‌پذیری افقی اپلیکیشن و جداسازی گزارش/Worker بر اساس سنجش.
- هیچ تغییر محیط عملیاتی بدون Change Approval و Runbook.

## 5. مدل داده هدف

### 5.1 قرارداد عمومی موجودیت‌ها
- شناسه داخلی GUID؛ کلید ترتیبی/ClusterKey در جداول حجیم.
- فیلدهای LegacyId، LegacyGuid، LegacySystem و LegacyNo در موجودیت‌های مهاجرتی.
- CreatedAt/CreatedBy، ModifiedAt/ModifiedBy، RowVersion و IsActive؛ Soft Delete در موارد مناسب.
- CenterId، SaleOfficeId، StockId و سایر Scopeها در تراکنش‌های مرتبط.
- مبلغ/قیمت/مقدار با Decimal و Currency/Unit روشن.
- اسناد تأییدشده Snapshot از مشخصات و قیمت زمان ثبت دارند.

### 5.2 اسکیماهای هدف
- **core:** سازمان، مرکز، دفتر، تقویم/سال مالی، واحدها، ارز، کدها و داده مرجع.
- **sales:** Customer، Product، PriceRule، DiscountRule، Order، Invoice، InvoiceLine، Return، Target و Commission.
- **inventory:** Warehouse/Stock، StockLevel، StockMovement، Voucher، Batch/Lot، Reservation و Allocation.
- **finance:** Payment، Receipt، Cheque، CustomerBalance، Ledger، Journal و GL سبک.
- **crm:** Tour، Route، Visit، GPS/Proof، CallCenter و تعاملات مشتری.
- **security:** User، Role، Permission، UserRole، RolePermission، DataScope، Device و Session.
- **platform:** Outbox، Job، IntegrationLog، Idempotency، FileMetadata، Audit و FeatureFlag.
- **rpt:** Read Model، Fact و Dimensionهای گزارش.

### 5.3 موجودیت‌های کلیدی و قواعد
1. **Organization/Center/SaleOffice/Stock/Path:** ساختار سازمانی، چندمرکزی، مسیر فروش و مسیر پخش.
2. **Customer:** کد، نام، اطلاعات تماس، کد ملی/اقتصادی، آدرس/موقعیت، گروه، اعتبار، مسیر، وضعیت، مالک فروش و Legacy reference.
3. **Product:** کد، نام، گروه، برند، نوع، واحدها، بارکد، GTIN/IRC در صورت نیاز، وضعیت و مشخصات نگهداری.
4. **PriceRule:** دامنه اعمال شامل کالا/گروه/نوع/برند/مشتری/گروه مشتری/فعالیت/سطح/منطقه/مرکز/دفتر/نوع سفارش/تاریخ/اولویت/ارز.
5. **DiscountRule/Condition:** نوع تخفیف، شروط ترکیبی، اولویت، سقف/کف، جایزه، محدودیت زمانی و قابلیت تأیید.
6. **Order:** شماره، سال، مرکز، مشتری، نوع سفارش، وضعیت، اقلام، قیمت/تخفیف Snapshot، اعتبار و مرجع پیش‌ویزیت.
7. **Invoice:** شماره، سال، مرکز، نوع، وضعیت، مشتری، اقلام، مالیات/عوارض/هزینه، تخفیف/اضافه، مبالغ و ارتباط به سفارش/تحویل.
8. **Return:** ارجاع به فاکتور/تحویل، اقلام، علت، وضعیت بازرسی، محل موجودی و اثر مالی.
9. **Tour/Distribution:** تور، مسیر، خودرو/راننده، فروشنده/ویزیتور، برنامه، بارگیری، تحویل و تسویه.
10. **Visit/CRM:** برنامه ویزیت، نتیجه، سفارش/عدم سفارش، موقعیت، پیگیری و تاریخچه.
11. **Inventory:** انبار، کالا، موجودی، رزرو، حرکت، سند، بچ/سری/انقضا و کارتکس.
12. **Treasury:** پرداخت/دریافت، روش، صندوق/حساب، چک، سررسید، وصول/برگشت و تخصیص به اسناد.
13. **GL:** سند روزنامه، سرفصل، بدهکار/بستانکار و ارتباط با زیرسیستم‌ها؛ دامنه دقیق باید با تصمیم D7 تعیین شود.
14. **Target/Commission:** دوره، هدف، عملکرد، فرمول پورسانت، تأیید و تسویه.
15. **Security/Platform:** هویت، نقش، DataScope، Audit، Outbox، Idempotency، فایل و یکپارچه‌سازی.

### 5.4 روابط و قواعد محاسباتی
- Customer یک‌به‌چند با Order، Invoice، Payment، Visit و Balance.
- Order یک‌به‌چند OrderLine و می‌تواند به Invoice و Delivery تبدیل شود.
- Invoice یک‌به‌چند InvoiceLine، PaymentAllocation و Return.
- Product به PriceRule، DiscountRule، StockLevel و Movement مرتبط است.
- StockMovement مرجع اصلی گردش؛ StockLevel نمای جاری/محاسبه‌شده و قابل بازسازی است.
- Payment/Receipt می‌تواند به چند سند تخصیص یابد؛ مانده از Ledger/Allocation قابل ردیابی باشد.
- اسناد قطعی حذف فیزیکی نمی‌شوند؛ اصلاح/ابطال با Workflow، دلیل و Audit انجام می‌شود.
- فرمول مبلغ فاکتور از بند 2.3، با سیاست گردکردن مصوب، در یک Domain Service واحد پیاده و در Golden Dataset آزمون می‌شود.
- اعتبار مشتری بر اساس سیاست تأییدشده شامل مانده، چک/تعهد و سقف اعتبار محاسبه می‌شود؛ فرمول نهایی از مالک مالی/فروش اخذ شود.
- قواعد پورسانت و تخفیف باید نسخه‌دار و بر اساس تاریخ مؤثر باشند.

# بخش سوم — طراحی عملکردی و یکپارچه‌سازی

- مدیریت شرکت/مرکز/دفتر/انبار/مسیر/سال مالی/واحد/ارز/گروه‌بندی‌ها.

- وضعیت‌های Draft/Submitted/Approved/Reserved/PartiallyFulfilled/Fulfilled/Cancelled طبق Workflow مصوب.

# بخش چهارم — مهاجرت داده، امنیت و گزارش

## 8. مهاجرت یک‌طرفه داده

### 8.1 معماری ETL
Source Read-only → Extract Snapshot → Staging → Profiling/Transform → Validation → Target Load → Reconciliation → Sign-off. هر اجرا RunId، زمان، نسخه نگاشت، تعداد خوانده/بارگذاری/ردشده و خطاهای قابل تکرار دارد.

### 8.2 اصول مهاجرت
- بارگذاری تکرارپذیر و Idempotent؛ کلیدهای Legacy حفظ شوند.
- هر رکورد یا Loaded شود یا Rejected با علت، مالک و تصمیم؛ رکورد بی‌صدا حذف نشود.
- نگاشت فیلدها نسخه‌دار و Data Dictionary قابل ردیابی باشد.
- داده‌های مرجع قبل از تراکنش‌ها؛ ترتیب وابستگی FK رعایت شود.
- داده‌های حساس رمزنگاری و دسترسی ETL حداقلی باشد.
- داده آرشیوی از داده عملیاتی تفکیک شود؛ دامنه تاریخ با تصمیم D2.

### 8.3 موج‌های مهاجرت
1. **Wave 0 — آماده‌سازی:** Snapshot، Schema، کدگذاری، Collation، تاریخ، سال مالی و RunId.
2. **Wave 1 — سازمان و پایه:** مرکز، دفتر، انبار، مسیر، واحد، ارز، سال مالی و کدهای مرجع.
3. **Wave 2 — کاربران و امنیت:** حساب‌های کاربری منتخب بدون رمز قدیم؛ نگاشت نقش و DataScope با تأیید مالک.
4. **Wave 3 — مشتری و کالا:** Customer، Product، گروه‌ها، بارکد، آدرس و موقعیت؛ استثناهای تکراری/ناقص.
5. **Wave 4 — قیمت و تخفیف:** قواعد فعال و تاریخ مؤثر، شروط، اولویت و آزمون رفتاری.
6. **Wave 5 — فروش:** سفارش، سطر سفارش، فاکتور، سطر فاکتور، مرجوعی و شماره‌های Legacy.
7. **Wave 6 — انبار:** انبار، موجودی، اسناد و سطرها، رزرو و کارتکس.
8. **Wave 7 — مالی:** پرداخت، چک، تخصیص، مانده مشتری و سند افتتاحیه/GL.
9. **Wave 8 — CRM/توزیع:** تور، مسیر، ویزیت و آخرین وضعیت/تاریخچه طبق D6.
10. **Wave 9 — Delta نهایی:** توقف نوشتن قدیم، Snapshot نهایی، استخراج Delta، بارگذاری و تطبیق.

### 8.4 ترتیب وابستگی
Organization/Reference → Customer/Product → Price/Discount → Order/Invoice/Return → Stock/Movement → Payment/Cheque/Balance → Tour/Visit/Distribution → Reporting/Opening Balances. ترتیب نهایی باید با FK/وابستگی واقعی و Data Dictionary تطبیق داده شود.

### 8.5 قواعد تبدیل و پاکسازی
- نرمال‌سازی فارسی/عربی در جست‌وجو بدون تخریب مقدار اصلی.
- کد ملی/موبایل/بارکد تکراری: تشخیص، مالک، Merge/Flag یا Reject مستند؛ Merge خودکار ممنوع.
- داده تماس/موقعیت ناقص: انتقال با Flag کیفیت؛ اجباری‌کردن فقط با تصمیم فرایندی.
- تاریخ شمسی: تبدیل با کتابخانه معتبر و تست کبیسه؛ نگهداری مقدار منبع برای ممیزی.
- AccYear: نگاشت از مقدار سال شمسی، نه ID جدول مرجع.
- SaleNo/OrderNo: یکتایی بر اساس سال و مرکز؛ تکرار بین مراکز مجاز طبق مدل.
- فاکتورهای بدون شماره: LegacyNo حفظ؛ برای 120 فعال، تصمیم مالک و شماره جدید طبق سیاست.
- مبلغ صفر/منفی و فرمول ناسازگار: Exception Register و تأیید مالی.
- مشتری بدون مانده: تعیین مانده صفر یا محاسبه‌شده با تأیید مالی.
- انبار بدون ردیف موجودی: ثبت موجودی صفر یا وضعیت خالی طبق تصمیم مالک.
- چک باز/سررسید: تطبیق با اسناد و وضعیت واقعی بانک؛ IsReconciled بدون تفسیر منتقل نشود.

### 8.6 تطبیق و آستانه‌ها
| شاخص | آستانه مرجع سند |
|---|---|
| Count هر جدول | 100% بارگذاری یا Reject مستند |
| جمع مبلغ فاکتور | اختلاف حداکثر 0.01% با مستندسازی گردکردن |
| مانده مشتری | اختلاف صفر؛ 92 مشتری بدون رکورد تعیین تکلیف |
| موجودی | اختلاف صفر؛ دو انبار بدون ردیف تعیین تکلیف |
| چک باز/سررسید | 100% تعیین تکلیف |
| فرمول فاکتور | 100% توضیح برای 310 مورد |
| شماره سند | 100% تعیین تکلیف؛ 120 فاکتور فعال بدون شماره |
| مبلغ <=0 | 100% توضیح برای 13 مورد (9 فعال) |
| AccYear | نگاشت 100% سال‌های 1402..1405 |
| GL | مجموع بدهکار = مجموع بستانکار |

تطبیق در سطح Count، Sum، Balance، Stock، شماره سند، سال مالی و نمونه‌گیری جزئی انجام شود. کوئری‌های پیوست H مرجع اجرای پروفایل و تطبیق‌اند؛ `NOLOCK` فقط برای Profiling و نه تطبیق نهایی.

### 8.7 Dry-Runها
- Dry-Run 1 (حدود T-45): صحت ETL، نگاشت، شمارش و ثبت استثنا.
- Dry-Run 2 (حدود T-30): UAT، تطبیق مالی/انبار، آموزش کلیدی و آزمون کارایی.
- Dry-Run 3 (حدود T-14): اجرای زمان‌بندی واقعی، تمرین Rollback، Freeze داده پایه و تأیید گزارش‌ها.
هر Dry-Run باید گزارش زمان، حجم، نرخ خطا، مغایرت‌ها، تصمیم و امضای مالک داشته باشد.

### 8.8 Cutover و Rollback
شمارش معکوس پیشنهادی:
- T-45: Dry-Run 1، تثبیت دامنه و Data Owner.
- T-30: Dry-Run 2، UAT، آموزش و Performance Test.
- T-14: Dry-Run 3، تمرین Rollback و تأیید گزارش‌ها.
- T-7: Backup کامل، تست Restore، دسترسی، Print Service و Go/No-Go اولیه.
- T-3: Freeze تغییرات کد و تأیید داده پایه.
- T-1: Backup نهایی، Delta، بارگذاری، تطبیق مالی/انبار و Read-only کردن قدیم.
- T0: Cutover طبق Runbook؛ فعال‌سازی دسترسی بعد از Gateها.
- T+1 تا T+14: Hypercare و تطبیق روزانه.
- T+30: پذیرش و انتقال به پشتیبانی عادی.
- T+90 تا T+365: آرشیو Read-only و بازنشستگی طبق الزامات حقوقی.

Rollback Trigger: اختلاف مالی/موجودی حل‌نشده، خطای بحرانی فاکتور/پرداخت، از دست رفتن داده، توقف عملیات بیش از 4 ساعت یا رخداد امنیتی. **نکته اجرایی حیاتی:** پیش از Go-Live باید صریحاً تعیین شود تراکنش‌هایی که پس از Cutover در سامانه جدید ثبت شده‌اند چگونه حفظ/بازپخش/تطبیق می‌شوند. Restore نسخه قدیم بدون تعیین تکلیف این تراکنش‌ها Rollback کامل محسوب نمی‌شود. روش بازگشت باید در محیط تمرینی اجرا و زمان RTO هدف کمتر از 4 ساعت اثبات شود.

## 9. امنیت، دسترسی و انطباق

### 9.1 احراز هویت

- اعمال مجوز در Handler/Query/Service و آزمون دسترسی افقی؛ UI تنها مرز امنیتی نیست.
- ثبت تغییر نقش/مجوز، Override اعتبار/تخفیف، ابطال و عملیات مالی.

### 9.4 PWA و زیرساخت
- حداقل‌سازی داده آفلاین، انقضا و حذف امن پس از Logout/Revocation.

- جداسازی شبکه، Patch، Firewall، Backup و تست Restore.
- Threat Model، SAST/DAST/SCA و Pentest مستقل پیش از Go-Live.
- انطباق مالیاتی/مودیان و نگهداری اسناد طبق نظر مشاور حقوقی/مالیاتی.

### 9.5 چک‌لیست امنیت پیش از Go-Live
Threat Model همه ماژول‌های حساس؛ SAST/DAST/SCA بدون یافته بحرانی/بالا؛ Pentest و رفع یافته؛ TLS/HSTS؛ MFA؛ RBAC/DataScope؛ عدم انتقال رمز قدیم؛ Secret Manager؛ Backup رمزنگاری‌شده و Restore؛ Audit؛ Rate Limit/Idempotency؛ Print Service امن؛ کنترل Upload؛ Incident Response.

# بخش پنجم — NFR، عملیات و برنامه تحویل

## 11. الزامات غیرعملکردی

### 11.1 اهداف مرجع
- SLA هدف: 99.5% در ساعات کاری.
- RTO هدف: 4 ساعت؛ RPO هدف: 15 دقیقه.
- RTL کامل، تقویم شمسی، فونت خوانا و UX مناسب شبکه 3G/ناپایدار.
- گزارش‌های سنگین از DB عملیاتی جدا باشند.
- کارایی باید در فاز صفر با سناریو، داده و بار واقعی نهایی شود؛ عدد بدون آزمون، تعهد پذیرفته‌شده نیست.

### 11.2 حوزه‌های NFR
1. Performance: زمان پاسخ p95 برای عملیات کلیدی، زمان گزارش و زمان Sync.
2. Capacity: کاربر هم‌زمان، نرخ ثبت سند، حجم فایل، رشد DB و فضای Backup.
3. Availability: Health Check، Redundancy و نگهداری برنامه‌ریزی‌شده.
4. Reliability/Recovery: Backup، Restore، DR، RTO/RPO و بازیابی Job/Outbox.
5. Security: MFA، least privilege، رمزنگاری، Audit و Patch.
6. Usability/Accessibility: RTL، موبایل، صفحه‌کلید، پیام خطای فارسی و جریان کوتاه.
7. Maintainability: ماژولار بودن، تست، ADR، مستندات و نسخه‌گذاری.
8. Observability: Log ساخت‌یافته، Metric، Trace، CorrelationId و Alert.
9. Compatibility: مرورگرهای هدف، دستگاه‌ها، چاپگرها و نسخه PWA.

### 11.3 معیارهای قابل اندازه‌گیری
در فاز صفر برای هر سناریو مقدار هدف، حجم داده، دستگاه، شبکه، p50/p95/p99 و معیار شکست تعیین شود. تست Load/Stress/Soak و ظرفیت SQL قبل از Cutover اجرا شود.

- Payment/Receipt، Cheque، Allocation و وصول.
- مانده مشتری و تطبیق.
- GL سبک یا خروجی حسابداری بر اساس D7.
**تحویل‌دادنی‌ها:** Inventory/Treasury، مالی، تطبیق موجودی/مانده و گزارش‌های P0/P1.
**خروج:** موجودی و مانده با اسناد نمونه تطبیق؛ چک و تخصیص قابل ردیابی؛ GL متوازن در صورت وجود.

### فاز 5 — توزیع و CRM (12 تا 14 هفته)
**کارها**
- Tour، Route، برنامه ویزیت و تخصیص خودرو/راننده.
- بارگیری، تحویل کامل/جزئی/ناموفق و تسویه.
- Van-Sale، موجودی خودرو و تسویه پایان شیفت.
- CRM، Visit، GPS و Proof در چارچوب سیاست داده.
- PWA Offline، Sync delta، Conflict Handling و تست شبکه ناپایدار.
**تحویل‌دادنی‌ها:** Distribution/CRM، PWA میدانی، Sync API و گزارش‌های مسیر/تحویل/ویزیت.
**خروج:** سناریوی میدانی انتها‌به‌انتها با قطع/وصل شبکه، عدم تکرار مالی و تطبیق تسویه.

### فاز 6 — هدف، پورسانت و گزارش (10 تا 12 هفته)
**کارها**
- هدف‌گذاری و محاسبه پورسانت.
- Read Model/Reporting DB و KPIها.
- جایگزینی گزارش‌های P0 و P1؛ سپس P2 بر اساس اولویت.
- داشبورد نقش‌محور و Drill-down.
- خروجی PDF/Excel/CSV و کنترل DataScope.
**تحویل‌دادنی‌ها:** Target/Commission، Report Catalog، داشبورد و معیار صحت KPI.
**خروج:** گزارش‌های P0 جایگزین و تأیید شده؛ گزارش‌های مالی با منبع تطبیق؛ عملکرد مطابق NFR.

### فاز 7 — مهاجرت و Cutover (10 تا 12 هفته)
**کارها**
- تکمیل ETL و Staging.
- اجرای Dry-Run 1/2/3 و رفع اختلاف‌ها.
- مهاجرت داده در موج‌ها و تطبیق Count/Sum/Balance/Stock/GL.
- UAT با کاربران واقعی تمام نقش‌ها.
- Pentest، Load/Stress، Backup/Restore و DR.
- آموزش، Runbook، برنامه ارتباطات و تصمیم Go/No-Go.
**تحویل‌دادنی‌ها:** Migration Evidence، Reconciliation Pack، UAT Sign-off، Security Report، Cutover/Rollback Runbook و صورت‌جلسه Go/No-Go.
**خروج:** عبور G0 تا G6؛ هیچ اختلاف مالی/موجودی حل‌نشده و هیچ نقص Critical/High باز.

### فاز 8 — تثبیت و بازنشستگی (4 تا 6 هفته)
**کارها**
- Hypercare، پایش روزانه و رسیدگی اولویت‌دار.
- تطبیق روزانه فروش، وصول، مانده، موجودی و اسناد.
- رفع خطا و آموزش تکمیلی.
- انتقال به پشتیبانی L1/L2/L3.
- Read-only کردن قدیم، آرشیو رمزنگاری‌شده و تست Restore.
- غیرفعال‌سازی سرویس‌های قدیم و بازنشستگی طبق تأیید حقوقی/مالی.
**تحویل‌دادنی‌ها:** Final Acceptance، Lessons Learned، Asset Retirement، Support Handover و Archive Evidence.
**خروج:** 30 روز پایداری و تطبیق روزانه بدون اختلاف حل‌نشده؛ پذیرش رسمی.

### مسیر بحرانی
تثبیت قواعد قیمت/تخفیف و اعتبار → طراحی داده و پلتفرم → فروش/انبار/مالی → توزیع/CRM → گزارش/UAT → سه Dry-Run → Cutover. فازهای داده، UX، امنیت و گزارش می‌توانند با کنترل وابستگی موازی شوند؛ مهاجرت نهایی و Cutover قابل موازی‌سازی با عملیات نوشتن قدیم نیست.

### Milestoneها
M0 Charter و تصمیم‌های D1-D8؛ M1 Architecture/ERD؛ M2 Platform Ready؛ M3 Pricing/Discount Approved؛ M4 Sales UAT؛ M5 Inventory/Finance Reconciled؛ M6 Field/PWA Pilot؛ M7 P0 Reports Accepted؛ M8 Dry-Run 3؛ M9 Go-Live؛ M10 Final Acceptance/Retirement.

### Pilot
پیشنهاد سند: یک مرکز توزیع (مرکز 1) به‌عنوان Pilot، مشروط به تأیید Sponsor و نمایندگی فرآیندهای واقعی. معیار انتخاب مرکز: حجم و تنوع کافی، Data Owner در دسترس، کاربر Champion، پوشش فروش/انبار/مالی/توزیع و امکان بازگشت عملیاتی. Pilot جایگزین ممنوعیت Dual-Run نیست؛ Pilot پیش از Cutover نهایی در محیط و دامنه کنترل‌شده انجام می‌شود و معماری همچنان مهاجرت یک‌طرفه باقی می‌ماند.

## 16. آزمون و پذیرش

### 16.1 سطوح آزمون
Unit، Integration، Contract/API، Component/UI، E2E، Migration، Performance، Security، Regression و UAT.

### 16.2 قواعد تست
- پوشش بیش از 80% برای منطق قیمت/تخفیف/اعتبار، همراه با کیفیت سناریو و نه صرفاً درصد پوشش.
- Golden Dataset شامل اسناد عادی، مرزی، ابطال، تخفیف چندگانه، مالیات، اعتبار، چندمرکزی و تاریخ مؤثر.
- تست DataScope برای تمام نقش‌ها و سناریوهای دسترسی افقی/عمودی.
- تست هم‌زمانی شماره سند، موجودی، رزرو و Idempotency عملیات مالی.
- تست PWA در قطع/وصل، Retry، Conflict، دستگاه گم‌شده و لغو دسترسی.
- تست مهاجرت با Count/Sum/Balance/Stock/GL و Legacy trace.
- SAST/DAST/SCA و Pentest؛ رفع Critical/High پیش از Go-Live.
- Load/Stress/Soak بر اساس NFR و Snapshot حجمی.

### 16.3 سناریوهای حیاتی Smoke/UAT
1. ورود، خروج، قفل حساب و MFA.
2. ایجاد/ویرایش مشتری با DataScope.
3. جست‌وجوی کالا و محاسبه قیمت/تخفیف.
4. ثبت سفارش، تأیید، رزرو و تبدیل به فاکتور.
5. فاکتور با مالیات/هزینه/تخفیف و چاپ.
6. ابطال/اصلاح با دلیل و Audit.
7. مرجوعی و اثر انبار/مالی.
8. دریافت وجه و تخصیص به فاکتور.
9. ثبت چک، سررسید، وصول و برگشت.
10. انتقال/خروج انبار و کارتکس.
11. بارگیری تور و تحویل کامل/جزئی/ناموفق.
12. فروش ونسل و تسویه خودرو.
13. ویزیت آفلاین و Sync بدون Duplicate.
14. گزارش P0 با DataScope.
15. گزارش مدیریتی و تطبیق KPI.
16. مؤدیان در Sandbox و رسیدگی به Retry/خطا.
17. Backup/Restore و بازیابی Outbox.
18. دسترسی افقی بین مراکز/مشتریان.
19. قطع سرویس خارجی و Fallback.
20. Cutover و سناریوی Rollback تمرینی.

### 16.4 معیارهای پذیرش
- هیچ نقص Critical/High باز.
- تمام جریان‌های حیاتی UAT Pass و Sign-off مالکان.
- تطبیق داده مطابق آستانه‌های بخش 8.
- DataScope و MFA اثبات‌شده.
- Backup/Restore و RTO/RPO تست‌شده.
- گزارش‌های P0 تأییدشده.
- NFR در بار مصوب پاس.
- Runbook، آموزش، Helpdesk و مانیتورینگ آماده.
- هیچ وابستگی Runtime به Legacy باقی نمانده.

### 16.5 مدیریت نقص
Severity، اولویت، مالک، نسخه بازتولید، Evidence، Root Cause و Retest برای هر Defect ثبت شود. نقص Critical/High مانع Gate است؛ پذیرش ریسک باید کتبی، زمان‌دار و با مالک مشخص باشد.

## 17. آموزش و مدیریت تغییر

### 17.1 گروه‌ها و برنامه
- مدیران: داشبورد، KPI، تأیید و گزارش؛ کارگاه مدیریتی.
- فروش/کال‌سنتر: مشتری، قیمت، سفارش، فاکتور و پیگیری؛ کارگاه و Sandbox.
- ویزیتور/راننده: PWA، ویزیت، تحویل، وصول و آفلاین؛ آموزش حضوری/میدانی.
- انبار: دریافت، برداشت، انتقال، شمارش و کارتکس؛ تمرین عملی.
- مالی: وصول، چک، مانده، GL و تطبیق؛ کارگاه تخصصی.
- IT/پشتیبانی: استقرار، پایش، Backup/Restore، عیب‌یابی و دسترسی؛ آموزش فنی.

### 17.2 مواد آموزشی و سنجش
راهنمای نقش‌محور فارسی، ویدئو/تصویر، FAQ، سناریوهای خطا، راهنمای آفلاین و چک‌لیست Cutover تهیه شود. کاربر باید با سناریوی عملی ارزیابی شود؛ صرف حضور در کلاس معیار پذیرش نیست.

### 17.3 مدیریت تغییر
شبکه Champion، اطلاع‌رسانی زمان‌بندی‌شده، ثبت بازخورد، تیکت، آموزش تکمیلی و سنجش نرخ خطا/تیکت/استفاده. تغییر فرآیند با مالک کسب‌وکار تصویب شود.

## 18. پشتیبانی، نگهداری و بازنشستگی قدیم

### 18.1 مدل پشتیبانی
- L1 میز خدمت: ورود، راهنمایی، تیکت و تشخیص اولیه.
- L2 تیم اپلیکیشن: نقص، تنظیمات و داده.
- L3 توسعه/معماری: نقص پیچیده، کد و طراحی.
- Incident P1/P2 باید RCA داشته باشد.

### 18.2 SLA پیشنهادی
| اولویت | تعریف | زمان پاسخ | هدف رفع/راهکار |
|---|---|---:|---:|
| P1 | توقف عملیات، داده غلط یا امنیت | 15 دقیقه | 2 ساعت راهکار / 8 ساعت رفع هدف |
| P2 | اختلال ماژول اصلی | 1 ساعت | 8 ساعت راهکار / 3 روز رفع |
| P3 | اختلال جزئی/کاربر محدود | 4 ساعت | 2 روز راهکار / 10 روز رفع |
| P4 | درخواست/بهبود | 1 روز | برنامه‌ریزی در Backlog |

### 18.3 نگهداری
اصلاحی (رفع باگ)، تطبیقی (قانون/سیستم‌عامل/درگاه)، پیشگیرانه (Patch، Backup، ظرفیت) و تکاملی (قابلیت جدید). بازبینی دسترسی فصلی، اسکن آسیب‌پذیری ماهانه، Patch بحرانی کمتر از 7 روز و Restore ماهانه در چک‌لیست عملیات قرار گیرد.

### 18.4 بازنشستگی Legacy
پس از پذیرش: توقف نوشتن، Backup نهایی، آرشیو رمزنگاری‌شده و Restore Test، لغو دسترسی کاربران، غیرفعال‌سازی NGT/FRU/API و Jobهای Sync، جمع‌آوری دانش، ابطال لایسنس غیرضروری و خاموشی سرورها پس از دوره Read-only. نگهداری اسناد تابع تأیید مالی/حقوقی است.

Cutover در صورت اختلاف مالی/موجودی، نقص امنیتی بحرانی، عدم آمادگی عملیات، UAT ناقص، Backup/Restore ناموفق، Rollback تمرین‌نشده یا نبود امضای مالکان متوقف شود. فشار زمان یا هزینه جایگزین معیار پذیرش نیست.

## وضعیت معماری مخزن مقصد
این نقشه‌راه از سند ShirinNovin مشتق شده و Stack پیشنهادی آن ASP.NET Core + SQL Server + React/Next PWA است. مخزن Green-DMS در زمان تهیه این سند Stack متفاوتی بر پایه NestJS/TypeScript، PostgreSQL/PostGIS، Next.js و Android دارد. این تفاوت، یک تصمیم معماری واقعی است و نباید با متن‌نویسی پنهان شود.

بنابراین این سند:
- برنامه محصول/سامانه مستقل وب فروش و پخش ShirinNovin را مستند می‌کند.
- به‌تنهایی مجوز تغییر Stack یا Database مخزن Green-DMS نیست.
- مجوز مهاجرت داده واقعی، تغییر محیط عملیاتی، Cutover یا حذف سامانه قدیم نیست.
- قبل از تبدیل‌شدن به Backlog توسعه Green-DMS نیازمند تصمیم رسمی مالک درباره رابطه دو محصول و ADR سازگاری/عدم سازگاری است.

## شکاف‌های باقیمانده نسبت به فایل مرجع 4,758 خطی
این نسخه، نقشه‌راه اجرایی تفصیلی و ساختارمند است و تمام سرفصل‌های 0 تا 19 و پیوست‌های A تا L را در قالب قابل اجرا پوشش می‌دهد؛ اما **رونوشت کلمه‌به‌کلمه سند 4,758 خطی نیست**. برای اجرای ETL، پیوست B باید با تمام تعریف ستون‌های Legacy، پیوست G باید با نگاشت ستون‌به‌ستون، پیوست H باید با متن کامل SQL و پیوست D باید با مقادیر تنظیمات مجاز تکمیل شود. این موارد باید از فایل اصلی مرجع استخراج و در مخزن به‌عنوان ضمائم فنی جداگانه نگهداری شوند؛ هیچ مقدار یا Query غایب در این نسخه حدس زده نشده است.
