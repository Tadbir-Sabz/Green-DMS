## D) تغییرِ دقیقِ منبع (P0 — QA-B1)

در `docker/postgres-init/10-runtime-role.sh` فقط بلوکِ توجیهی و بدنهٔ حلقه تغییر کرد:

```bash
for _t18_var in $(compgen -e); do
  if [ "${!_t18_var-}" = "$RUNTIME_PASSWORD" ]; then
    export -n "$_t18_var"
  fi
done
```

(قبلاً یک `case "$_t18_var" in PGPASSWORD | PGPASSFILE) continue ;;` نام‌ها را بدونِ
نگاه به مقدار معاف می‌کرد.) رفتارِ حاصل:

* **مقدارِ غیرهم‌مقدارِ `PGPASSWORD`/`PGPASSFILE`**: آزمونِ مقدار نمی‌خورد ⇒ دست‌نخورده
  ⇒ احرازِ مشروعِ libpq دقیقاً مثلِ قبل (اثباتِ رفتاری: پیکربندِ «متفاوت» در هارنسِ ۳f-۱
  و تستِ L1 با احرازِ واقعیِ scram).
* **مقدارِ هم‌مقدار**: همان رمز زیرِ نامِ دیگر است ⇒ مانندِ هر alias دیگر `export -n`
  می‌شود. `PGPASSWORD` یک مقدارِ رمز و `PGPASSFILE` یک رشتهٔ مسیر است — هر دو با همان
  معیارِ مقدار سنجیده می‌شوند.
* **حالتِ نامتعارفِ «برخورد + احرازِ رمزیِ TCP»**: psql بدونِ آن رمز وصل نمی‌شود و
  `ON_ERROR_STOP` اسکریپت را با خروجِ غیرصفر متوقف می‌کند — **fail-closed**، نه
  provision با credentialِ export‌شده. مسیرِ پشتیبانی‌شدهٔ نخستین بوت (سوکتِ trust) بدونِ
  رمز کار می‌کند و اصلاً به این مورد نمی‌رسد.
* سایر مکانیزم‌ها دست‌نخوردند: `unset` دو نامِ اعتبارنامه، `export -n RUNTIME_PASSWORD`،
  ترتیبِ scrub پیش از هر فرزند، گاردهایِ fail-closed، `printf | psql -f <(cat …)` و
  `\password`ِ stdin-only. دیفِ اسکریپتِ init در این کامیت `+29/−21` (فقط همین بلوک و
  کامنت‌ها) است.

هیچ مکانیزمِ credentialِ تازه‌ای (فایلِ pgpass موقت و …) معرفی نشد — طبقِ دستور، چون
پیکربندِ امنِ موجود (سوکتِ trust در جریانِ entrypoint) نیاز را برآورده می‌کند.
