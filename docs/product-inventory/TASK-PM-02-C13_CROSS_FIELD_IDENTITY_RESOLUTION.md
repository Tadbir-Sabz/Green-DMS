## بخش ۲ — Workstream A: فضای مقایسهٔ مشترک

### چرا پروفایل‌هایِ میدانی کافی نبودند

```
alias   '400 111'  →  ProductAlias  →  '400 111'   (فاصله حفظ)
barcode '400111'   →  Barcode       →  '400111'    (فاصله حذف)
                                        ⇒ دو کلیدِ متفاوت ⇒ برخورد دیده نمی‌شود
```

### راه‌حل: چهار فضا، سه‌تایِ آن‌ها به میدان وابسته نیستند

| فضا | تبدیل | وابسته به میدان؟ |
| --- | --- | --- |
| `field` | پروفایلِ اختصاصیِ میدان (C11) | **بله** (عمدی) |
| `scan` | NFKC → ارقامِ لاتین → کوچک‌سازی → حذفِ همهٔ جداکننده‌ها (صفرِ ابتدایی حفظ) | **نه** |
| `alnum` | همان، ولی فاصلهٔ درونی حفظ و نشانه‌گذاری حذف | **نه** |
| `text` | `SearchKey` از C11 (اعراب حذف، ي/ك یکسان، آ/أ متمایز) | **نه** |

**تقارن ضمانتِ اصلی است.** چون تابعِ فضایِ `scan` به میدان وابسته نیست، هر دو طرفِ مقایسه
دقیقاً یک تبدیل می‌گیرند. اگر وابسته بود، همان اشتباهِ CF-10 تکرار می‌شد.

### جدولِ اعلانیِ ۱۵ جفت (قرارداد `c13.1`)

| جفت | فضا | تصمیم | شدت | تصویب لازم |
| --- | --- | --- | --- | --- |
| alias ↔ barcode | scan | **HARD_CONFLICT** | hard | بله |
| alias ↔ code | alnum | **HARD_CONFLICT** | hard | بله |
| barcode ↔ code | scan | **HARD_CONFLICT** | hard | بله |
| alias ↔ name | text | SOFT_CONFLICT | soft | نه |
| alias ↔ name_latin | text | SOFT_CONFLICT | soft | نه |
| name ↔ name_latin | text | MANUAL_REVIEW | review | بله |
| code ↔ name | alnum | MANUAL_REVIEW | review | نه |
| code ↔ name_latin | alnum | MANUAL_REVIEW | review | نه |
| barcode ↔ name | scan | **NOT_COMPARABLE** | none | نه |
| barcode ↔ name_latin | scan | **NOT_COMPARABLE** | none | نه |
| ۵ جفتِ هم‌میدانی | field | ۳ hard · ۲ soft | — | نه |

میدانی که جدول تعریفش نکرده باشد ⇒ **خطا**، نه سکوت. تستِ پوشش همهٔ ۱۵ جفت را می‌سنجد.

### «هر شباهتِ متنی تعارض نیست» — سنجیده، نه ادعا

| نمونه | تصمیم | چرا |
| --- | --- | --- |

| دو کالا نامِ یکسان | `SOFT_CONFLICT` | نام می‌تواند مشروع مشترک باشد |

| alias یکسان برایِ همان کالا | `ALLOWED` | افزونگیِ ذخیره‌سازی، نه ابهام (**اصلاحِ C12**) |

## بخش ۳ — Workstream B: موتورِ تصمیم

هر نتیجه **همهٔ** میدانهایِ خواسته‌شده را حمل می‌کند:

`collision_id` (`C13-<8hex>`، مستقل از ترتیب، پایدار) · طرفین · نوعِ میدان · شرکت/دامنه ·
مقادیرِ اصلی · کلیدهایِ canonیک · `rule_id` + `contract_version` + `normalization_version` ·
توضیحِ فارسی · شدت · توصیهٔ انسانی · `provenance` · `confidence` · `ambiguity`.

### دو ناسازگاریِ موجود که C13 آشکار کرد

1. **D-C11-3 امروز زنده است:** قیدِ پایگاه‌داده حساس به حروف است ولی بررسیِ برخورد نامحسوس.
   موتورِ C13 جفتِ `SKU-9`/`sku-9` را `HARD_CONFLICT` می‌بیند، در حالی که قیدِ فعلی اجازهٔ
   وجودشان را می‌دهد. **این ناسازگاری پیش از C13 هم وجود داشت.**
2. **C12 هر تجمعِ alias را hard می‌شمرد**، حتی وقتی هر دو ردیف به یک کالا تعلق داشتند.
   اصلاح شد: `ALLOWED` با قاعدهٔ `C13-R-redundant-row`.

### هیچ ادغام/حذف/بازنویسی

هر توصیهٔ `HARD_CONFLICT` به تصمیمِ انسانی ارجاع می‌دهد؛ تست این را با الگویِ زبانی می‌سنجد
(نه با وجودِ واژه، چون واژه می‌تواند در **نفی** بیاید).

## بخش ۴ — Workstream C: RLS و جداسازیِ دامنه

⚠️ این تست‌ها **DB-free** هستند. آنچه اثبات می‌شود **قراردادِ افشای موتور** است، نه RLS
پایگاه‌داده. RLS لایهٔ اصلی است و **دست‌نخورده** مانده؛ این لایهٔ دومِ دفاعی است
(*defense in depth*).

| سناریو | نتیجه |
| --- | --- |
| برخوردِ درون‌شرکتی | مقدار قابلِ مشاهده (کاربرِ همان شرکت) · هرگز دو شرکت مخلوط نمی‌شوند |
| شناسهٔ یکسان در دو شرکت | `ALLOWED` · **مقدار `null`** · شناسه‌ها و `source_ref` هش‌شده |
| بین‌دامنه در همان شرکت | `MANUAL_REVIEW` · مقدار قابلِ مشاهده (هر دو طرفِ همان شرکت) |
| مالکیتِ متفاوت | برخوردِ درون‌شرکتی ساخته نمی‌شود |
| تلاشِ مقایسهٔ غیرمجاز | هیچ گزینه‌ای برای خاموش‌کردنِ پوشاندن **وجود ندارد** |

### آزمونِ خصمانهٔ نشت

۵۰ شرکت، ۵ شناسهٔ متمایز در هم تنیده:

```json
{ "companies": 50, "distinct_identifiers": 5,
  "raw_values_leaked": 0, "source_refs_leaked": 0,
  "conflicts_still_detected": 5 }
```

**این آزمون یک باگِ واقعی پیدا کرد:** `parties` پوشانده می‌شد ولی `provenance` همان
`source_ref` خامِ شرکتِ دیگر را لو می‌داد — داده از دریچهٔ عقب بیرون می‌رفت. رفع شد و اکنون
هر دو مسیر از یک قاعده پیروی می‌کنند.

### توالیِ پیشنهادیِ C14 (اجرا نشده)

1. **حلِ دروازهٔ Windows** — یا تأییدِ رسمی که Linux پذیرفته است، یا اجرایِ مجدد در محیطِ Windows.
2. **گرفتنِ نسخهٔ مجازِ داده** با شش شرطِ بخشِ ۵ و اثباتِ اجراییِ ردِ نوشتن.
3. **تصویبِ D-C11-1…6 و D-C12-1…3 و D-C13-1** توسطِ مالکِ کسب‌وکار.
4. اجرایِ ارزیابیِ سایه‌ای روی دادهٔ مجاز و تحویلِ دفتر به مالک.
5. حل‌وفصلِ دستیِ برخوردهایِ `HARD_CONFLICT` (هیچ ادغامِ خودکار).
6. `CREATE UNIQUE INDEX CONCURRENTLY` روی کلیدِ نامزد — فقط پس از صفر شدنِ hard.
7. dual-read، سپس بازمحاسبهٔ batch‌به‌batch با backup و تمرینِ بازگشت.
8. فعال‌سازی = **دروازهٔ تصویبِ جداگانه** با مالک + امنیت.
