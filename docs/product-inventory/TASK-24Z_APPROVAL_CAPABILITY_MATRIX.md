## خواندنِ ماتریس — چرا ۳ مورد «کامل» و ۴ مورد «باز» است

سه عملیاتِ ردیفِ ۱–۳ **به‌طورِ کامل** از گردشِ واحدِ تأیید عبور می‌کنند:

```
POST /orders/{id}/request-approval   (یا /returns/... یا /purchase-orders/...)
   → submitForApproval()  → approval_request + approval_binding (یک تراکنش)
   → POST /rules-engine/approvals/{id}/decision  (هر مرحله، با منعِ خودتأییدی)
   → POST /orders/{id}/approve
       → consumeApprovedBinding(companyId, {operation, entityType, entityId, fingerprint}, execute)
           1) SELECT ... FOR UPDATE OF b           ← قفلِ اتصال
           2) recompute fingerprint و مقایسه        ← اگر تغییر کرده: 409
           3) UPDATE binding SET consumed_at=now()  ← مصرف
           4) execute()  (تغییرِ وضعیتِ موجودیت)
           ── هر خطا ⇒ ROLLBACK کلِ تراکنش (تأیید نمی‌سوزد)
```

چهار عملیاتِ ردیفِ ۴–۷ امروز فقط با **مجوز (permission)** محافظت می‌شوند، نه با
**گردشِ تأیید**. این یک شکافِ آگاهانه است، نه فراموشی:

- `purchase_request` (P1): درخواستِ خرید پیش از تبدیل به سفارشِ خرید است؛ اثرِ مالی
  نهایی در `purchase_order` اعمال می‌شود که **دروازه دارد**. ریسک باقی‌مانده: دورزدنِ
  کنترلِ بودجه در مرحلهٔ درخواست.
- `treasury_day_close` (P2): بستنِ روز برگشت‌پذیر است (بازگشایی مجاز)، ولی نیاز به
  گردشِ تأییدِ دو‌نفره دارد تا یک نفر نتواند روز را ببندد.
- `customer_price` / `price_change_log` (P2): تغییرِ قیمتِ مشتری و ثبتِ تغییرِ قیمت
  هنوز فقط مجوزمحورند.

**هیچ‌کدام از این چهار مورد «تأییدِ جعلی» نمی‌سازند**: آن‌ها اصلاً وارد گردش نمی‌شوند،
پس هیچ تأییدی برای مصرف وجود ندارد.

## قواعدِ ترکیبِ سیاست (خلاصه — جزئیات در `docs/product-inventory/TASK-24Z_POLICY_COMPOSITION.md`)

1. **سیاستِ مرکزی همیشه حاکم است**: دامنه می‌تواند سخت‌گیرتر شود، هرگز سهل‌گیرتر نه.
2. **مراحل جمع می‌شوند** (نه انتخابِ یکی) — بیشترین تعدادِ مرحله برنده است.
3. **حداقلِ تعدادِ تأییدکننده** = بیشینهٔ همهٔ سیاست‌های منطبق.
4. **جداسازیِ وظایف** = سخت‌گیرانه‌ترین مقدارِ خواسته‌شده.
5. **تعارضِ صریح** (مثلاً دو سیاستِ مرکزی با حداقل‌های ناسازگار) ⇒ رد با پیامِ فارسی،
   نه انتخابِ ساکتِ یکی.
