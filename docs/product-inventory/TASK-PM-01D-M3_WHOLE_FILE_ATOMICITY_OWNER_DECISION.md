## ۱) تمایز دقیق مفاهیم (پیش از پرسش)

| مفهوم | تعریف عملیاتی | وضعیت فعلی |
|---|---|---|
| **اتمیّت هر دسته (per-batch atomicity)** | فایل به دستههای ۱۰۰تایی تقسیم میشود. هر دسته در یک تراکنش مستقل است: یا تمام ردیفهای همان دسته commit میشوند یا هیچکدام. شکست دسته، تراکنشهای دستههای پیشین را باطل نمیکند. | **پیادهمشده / مصوب §E / حفظشده در M3** |
| **اتمیّت کل فایل (whole-file atomicity)** | همهٔ دستهها باید نتیجهای واحد داشته باشند: اگر دستهٔ ۷ شکست خورد، اثر دستههای ۱ تا ۶ نیز undo یا جبران شود؛ خروجی نهایی «همهٔ ردیفها» یا «هیچ ردیفی» است. | **تصمیم نشده / پیاده نشده** |
| **موفقیت جزئی بین دستهها (partial success)** | دستههای موفق باقی میمانند، دستهٔ شکستخورده ثبت میشود، و طبق §E اجرای دستههای بعدی ادامه مییابد. نتیجهٔ فایل میتواند `completed` با خطا، `failed` با ردیفهای committed، یا وضعیت صریح `partial` باشد. | **رفتار فعلی M2**؛ نمایش دستهبه دسته در UI و `product_import_batch` |
| **تکرار/بازیابی (retry/recovery)** | ارسال همان `idempotency_key` نتیجهٔ terminal را بدون اثر دوباره replay میکند. رکورد `processing` رهاشده از مکاننما resume میشود. نتیجهای که بعد از قطع ارتباط قابل اثبات نیست (`unknown`) با توقف «بررسی اپراتور» مشخص میشود، نه حدس موفقیت. | **پیادهمشده در M2**؛ retry خودکارِ صرفاً ردیفهای ناموفق و سیاست «کل فایل» تعریف نشده |

تفاوت کلیدی: «همهیاهیچ در هر دسته» در برابر خطای همان دسته محافظت میکند، ولی
در برابر خطای دستهای دیگر، **فایل را همهیاهیچ نمیکند**. «موفقیت جزئی» دقیقاً
همان حالتی است که تصمیم مالک باید تکلیف آن را روشن کند.

## ۲) آنچه امروز واقعاً وجود دارد

- `product_import_batch`: وضعیت `committed|failed|rejected|rolled_back`،
  `transaction_outcome`، `failure_category`، `cursor` و `attempts` به ازای هر دسته،
  با RLS شرکت و grantهای `SELECT/INSERT/UPDATE` برای `dms_app` (بدون `DELETE`).
- تاریخچهٔ `0060` و ممیزی `audit_log` برای ردیفهایی که واقعاً commit شدهاند،
  تغییرناپذیر remain میکنند؛ undo ضمنی وجود ندارد.
- UI import نتیجهٔ کلی، دستهها، پیام فارسی، قابلیت retry امن و توقف unknown را نشان
  میدهد؛ فهرستی سراسری از فایلها و دکمهٔ «ادامهٔ فقط دستههای ناموفق» ندارد.
- هیچ worker/صف BullMQ برای import محصول در معماری پیادهمشده نیست؛ اجرا HTTP همزمان
  است. M3 این واقعیت را عوض نکرد.

## ۳) پرسشهای صریح از مالک / Product Owner / IAM / امنیت

پاسخ هر پرسش باید همراه با دلیل کسبوکاری، مرجع تصویب و پذیرش تست باشد. گزینهها
پیشنهاد نیستند و هیچکدام بهعنوان انتخاب ثبت نشدهاند.

### Q1 — آیا فایل CSV باید «همه یا هیچ» باشد؟
- الف) بله: شکست هر دسته ⇒ هیچ ردیفی از آن فایل باقی نماند.
- ب) خیر: همان رفتار «هر دسته» + ادامه حفظ شود.
- ج) فقط برای کلاس خاصی از خطاها (مثلاً validation) همهیاهیچ، و برای خطاهای زیرساختی موفقیت جزئی.

**پیامد الف:** نیاز به تراکنش سراسری، compensate/undo امن، یا مرحلهبندی؛ تداخل با
تاریخچهای که قبلاً commit شده و با idempotency replay باید حل شود. بدون طراحی و تست
جدید قابل ادعا نیست.

### Q2 — آیا دستههای موفق مجازند بعد از شکست دستهای دیگر **committed بمانند**؟
- الف) بله، با نمایش صریح «موفقیت جزئی» و ردیفهای باقیمانده.
- ب) خیر، باید حذف/جبران شوند (حالت Q1-الف).
- ج) بله ولی فقط تا سقف/آستانه مشخص، و بعد از آن توقف کامل.

**پیامد ب:** جبران نباید تاریخچهٔ immutable یا ممیزی را بازنویسی کند؛ به معنای
رخداد جبرانی جدید نیاز دارد و مالک باید معنای گزارش تاریخی را تصویب کند.

### Q3 — کاربر چگونه فایل نیمهتمام را retry کند؟
- الف) همان فایل + همان `idempotency_key` ⇒ فقط replay نتیجهٔ قطعی؛
- ب) فایل اصلاحشده + کلید تازه ⇒ اجرای مستقل (با خطر تکرار معنایی ردیفها)؛
- ج) UI «ادامه از آخرین دستهٔ سالم / فقط دستههای ناموفق»؛
- د) توقف و دخالت اپراتور برای هر `unknown`.

**نیاز به تصویب:** تعریف اینکه retry «همان عملیات» است یا «عملیات تازه»؛ نحوهٔ جلوگیری
از درج دوباره؛ و رفتار قطع شبکه پیش از دریافت ACK.

### Q4 — وضعیت فایل و دسته چگونه نمایش داده شود؟
- وضعیت فعلی `processing|completed|failed` به همراه آرایهٔ دستهها و فیلدهای
  `outcome/category/retryable` کافی است؟
- یا وضعیت سطح فایل تازهای مانند `partial|compensated|needs_operator_review` لازم است؟
- آیا شمارش `created_rows/updated_rows/failed_rows` باید «پس از جبران» بازمحاسبه
  شود یا همچنان واقعیت تراکنشهای انجامشده را نگه دارد؟

**نیاز به تصویب:** vocabulary قطعی، قرارداد API/کلاینت، برچسب فارسی RTL و تست درفت.

### Q5 — الزامات ممیزی و یکپارچگی تاریخچه چیست؟
- آیا ردیف commitشده و سپس جبرانشده، دو رخداد تاریخی جدا دارد یا یک رخداد نهایی؟
- آیا `audit_log` و `product_catalog_history` فقطافزودنی باقی بمانند؟ (موضع فعلی: بله)
- چه کسی مجاز است جبران/تغییر وضعیت را تأیید کند و آیا تأیید دوم-person لازم است؟
- retention، گزارشدهی به حسابرس و نمایش «وضعیت قدیمی در برابر وضعیت جبرانشده» چگونه باشد؟

4. تستهای قرارداد، DB بومی، RLS، تاریخچه، ممیزی و UI پیش از پیادهسازی هر تغییر رفتار.
5. بهروزرسانی §E، `TASK-PM-01D-M2_IMPLEMENTATION.md` و `EVIDENCE_INDEX.md` **پس از**
   تصویب، نه قبل از آن.

## ۵) مرز اجرای M3

- M3 فقط خروجی CSV خواندنی افزود؛ هیچ پاسخی از طرف مالک فرض نشد.
- هیچ `0061`، رفتار commit، grant، RLS، صف BullMQ، عضویت دامنه، شناسه دامنه،
  vocabulary مجوز تازه، یا تغییر معنای تاریخچهای اضافه نشد.
- تا زمان بند ۴، وضعیت این پرونده **BLOCKED / OPEN / NOT APPROVED** است؛ استفاده از
  عبارت «approved» بدون شواهد بند ۴ ممنوع است.


## ۶) یادداشت M4 — جداسازی صریح، بدون هیچ تصویب تازه

M4 یک «عملیات نگهداشت گروهی محدود» با حداکثر ۱۰۰ کالا و ۹ فیلد مرکزی اضافه
کرد که برای همان گزینش، همه یا هیچ است. این رفتار پاسخ Q1 تا Q5 بالا نیست،
§E و `0061` را تغییر نمیدهد، مجوز جبران/تأیید دونفره ایجاد نمیکند و هیچ سلول
جدول تصویب مالک را پر نمیکند. پرونده همچنان **BLOCKED / OPEN / NOT APPROVED**
است؛ استفاده از واژهٔ «approved» برای whole-file import، صرفاً بهدلیل سبزشدن M4،
ممنوع است. جزئیات فنی M4 در `TASK-PM-01D-M4_IMPLEMENTATION.md` آمده است.
