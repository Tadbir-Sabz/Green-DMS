## ۲) اثرِ قرارداد بر هر میدان

### ۲-۱) `alias_norm` — ریسکِ **بالا**

**تغییرِ رفتاری:** قراردادِ `ProductAlias` اضافه می‌کند: یکسان‌سازیِ `ي/ى/ك/ة`، حذفِ اعراب/تطویل،
تبدیلِ نیم‌فاصله/ZWJ/NBSP به فاصله، یکسان‌سازیِ نشانه‌گذاری (`، → ,`، `– → -`).

**پیامد:** بسیاری از مقدارهای موجودِ `alias_norm` **عوض می‌شوند**.

| سناریو | امروز | تحتِ قرارداد | پیامد |
| --- | --- | --- | --- |
| دو کالا با `علي` و `علی` | دو کلیدِ متفاوت | یک کلید | **برخوردِ تازه** |
| دو کالا با `كوكا` و `کوکا` | دو کلیدِ متفاوت | یک کلید | **برخوردِ تازه** |
| یک کالا با `کوکا‌زیرو` و دیگری با `کوکا زیرو` | متفاوت | یکسان | برخوردِ تازه (تصمیم D-C11-5) |

**خطرِ اصلی:** اگر **هم‌زمان** با بازمحاسبه، قیدِ یکتاییِ سطحِ شرکت فعال شود، `ALTER TABLE … ADD
CONSTRAINT` **شکست می‌خورد** و مهاجرت نیمه‌کاره می‌ماند.

### ۲-۲) `product.code` — ریسکِ **بالا**

**ناسازگاریِ موجود:** قید `case-sensitive` است ولی همهٔ مقایسه‌ها `lower()` می‌کنند.
یعنی `ABC` و `abc` می‌توانند هر دو ذخیره شوند، در حالی که منطقِ برنامه هر دو را یکی می‌بیند.
قرارداد `ProductCode` این را **case-insensitive** می‌کند ⇒ اگر چنین جفتی وجود داشته باشد،
قیدِ یکتاییِ تازه شکست می‌خورد.

همچنین: کدِ `۱۲۳` و `123` امروز دو کدِ متفاوت‌اند (چون `code` خام ذخیره می‌شود و `foldDigits` فقط
در جست‌وجو به‌کار می‌رود) ولی قرارداد هر دو را `123` می‌کند.

### ۲-۳) `product_barcode.barcode` — ریسکِ **متوسط**

**تغییر:** حذفِ انواعِ خطِ تیره + یکسان‌سازیِ حروفِ کوچک برای بارکدهای alphanumeric.

| سناریو | امروز | تحتِ قرارداد |
| --- | --- | --- |
| `123-456` ذخیره‌شده | `123-456` | `123456` |
| `INT-0042` | `int0042` (already lowercased? **خیر**) | `int0042` |

⚠️ **صفرِ ابتدایی:** `normalizeBarcode` امروز صفرِ ابتدایی را حذف **نمی‌کند** و قرارداد هم
**نخواهد کرد**. این نقطه با تست قفل شده است.

### ۲-۴) `product.name` / `name_latin` — ریسکِ **پایین**

قرارداد فقط **کلیدِ مقایسه** می‌سازد؛ مقدارِ نمایشی هرگز بازنویسی نمی‌شود. هیچ مهاجرتِ دادهٔ
نمایشی لازم نیست. تنها اگر «هشدارِ شباهت» (similar-name warning) بخواهد روی کلیدِ تازه کار کند،
یک ایندکسِ مشتق لازم می‌شود (بدونِ تغییرِ داده).

انجام شود. این یک **الزامِ طراحیِ C12** است، نه چیزی که C11 اجرا کند.


## ۵) استراتژیِ rollback

| فاز | rollback |
| --- | --- |
| فاز ۲ (dual-read) | حذفِ کدِ محاسبهٔ کلیدِ تازه؛ داده تغییر نکرده ⇒ rollback بی‌ریسک |
| فاز ۳ (بازمحاسبه) | **نیازمندِ backup**: مقدارِ قبلیِ `alias_norm`/`barcode` در جدولِ `*_norm_backup` نگه داشته شود تا بازگردانیِ دقیق ممکن باشد |
| فاز ۴ (رفعِ دستی) | ممیزیِ ردیف‌به‌ردیف لازم است؛ بدونِ backup **بازگشت‌ناپذیر** |
| فاز ۵ (قید) | `DROP CONSTRAINT` ساده |
| فاز ۶ (ایندکس) | `DROP INDEX` و بازسازی |

**قاعده:_** هیچ‌گاه فاز ۳ را بدونِ نسخهٔ پشتیبانِ ستون‌های هویتی اجرا نکنید.

## ۶) امکان‌سنجیِ dual-read / dual-write

| گزینه | امکان | یادداشت |
| --- | --- | --- |
| **dual-read** (محاسبهٔ هر دو کلید، تصمیم بر قدیمی) | **بله، کم‌ریسک** | فقط یک ستونِ مشتقِ اضافی یا محاسبهٔ درون‌حافظه‌ای لازم است؛ هیچ رفتارِ کاربری عوض نمی‌شود |
| **dual-write** (نوشتنِ هر دو کلید) | **با احتیاط** | نیازمندِ ستونِ تازه (مهاجرت) و ریسکِ واگرایی اگر یک مسیر به‌روز نشود |
| **shadow index** (ایندکسِ موازیِ کلیدِ تازه) | **بله** | اجازه می‌دهد تعارض‌ها **قبل** از هر تغییری دیده شوند — بهترین گزینه برای فاز 1/3 |

**توصیه:** فاز ۳ را با **shadow index** انجام دهید: ایندکسِ یکتای موازی روی کلیدِ تازه بسازید.
اگر ساختِ آن شکست خورد، **همان لحظه** فهمیدید چند تعارض وجود دارد — بدونِ تغییرِ یک ردیف داده.

## ۸) RLS و جداسازیِ شرکت/دامنه

- همهٔ جدول‌های هویتی `FORCE ROW LEVEL SECURITY` دارند و سیاست بر `company_id = fn_current_company_id()` است.
- قرارداد **هیچ** قاعدهٔ یکتاییِ سراسری پیشنهاد نمی‌کند ⇒ مرز حفظ می‌شود.
- **استثنای موجود:** `uq_product_barcode_gs1` سراسری است (فقط `gs1_*`). این تصمیمِ پیشین است و
  C11 آن را تغییر نداد؛ ولی هر بازنگریِ D1 باید این استثنا را آگاهانه بپذیرد یا رد کند.
- بازمحاسبهٔ `alias_norm` با نقشِ برنامه (`dms_app`) انجام‌شدنی است (`UPDATE` مجاز است)، ولی
  `product_catalog_history` **فقط-افزودنی** است و این بازمحاسبه ردیفِ تاریخچه تولید می‌کند —
  حجمِ تاریخچه باید پیش‌بینی شود (میلیون‌ها ردیف در سازمانِ بزرگ = ریسکِ حجم/کارایی).
