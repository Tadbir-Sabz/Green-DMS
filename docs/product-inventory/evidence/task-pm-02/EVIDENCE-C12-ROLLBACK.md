## ۱ — چه چیزی بازگشت‌پذیر است و چه چیزی نیست

| تغییر | بازگشت‌پذیر؟ | چرا |
| --- | --- | --- |
| `stored_normalized` (کلیدِ مقایسه) | ✅ **بله**، با backup | مقدارِ قبلی در `backup` نگه داشته می‌شود |
| `display_value` | ➖ **هرگز تغییر نمی‌کند** | خارج از دامنهٔ مهاجرت؛ ۲۴/۲۴ در هر اجرا حفظ شد |

| **حذفِ alias** | ❌ **بازگشت‌ناپذیر** | ⇒ **در C12 انجام نمی‌شود** |
| فعال‌سازیِ منطقِ مقایسهٔ تازه | ⚠️ با انتشارِ مجدد | ولی موجِ مهاجرت را متوقف نمی‌کند |

## ۲ — نتیجهٔ اجرای واقعی

```json
"rollback": { "restored": 24, "unrecovered": [], "returns_to_original": true, "display_untouched": true }
```

- **`restored: 24`** — همهٔ ۲۴ ردیفی که مقدارشان بازمحاسبه شده بود، به مقدارِ اولیه برگشتند.
- **`unrecovered: []`** — هیچ ردیفِ غیرقابل‌بازیابی نماند.
- **`returns_to_original: true`** — برابریِ کاملِ وضعیتِ نهاییِ بازگشت‌شده با وضعیتِ **اولیه**
  (`equivalentStates(initialState, rollback(full).state)`).

### یک باگ که همین تست پیدا کرد

نسخهٔ اولِ `rollback` مقدارِ `unrecovered` را با مقایسهٔ یک مقدار **با خودش** می‌سنجید و همیشه
صفر برمی‌گرداند — یعنی «بازگشتِ کامل» را **دروغ** می‌گفت. اصلاح شد: اکنون ردیفی که فازش
`recalculated` است ولی ورودیِ `backup` ندارد، به‌درستی «بازیابی‌نشده» شمرده می‌شود.
⇒ درس: یک بازگشتِ سبز هم می‌تواند بی‌معنا باشد اگر سنجه‌اش خودارجاع باشد.

## ۳ — بازیابی از قطعِ وسطِ کار

```json
"interruption_and_recovery": { "injected_fail_after_ops": 5, "interrupted": true,
  "ops_before_stop": 5, "recovered": true, "same_final_state_as_full_run": true }
```

شکست پس از ۵ عملیات تزریق شد. `resumeSimulation` از همان نقطه ادامه داد و به **همان وضعیتِ
نهاییِ اجرای بدونِ وقفه** رسید. یعنی مهاجرت **قابلِ ادامه** است و لازم نیست از صفر شروع شود.

## ۴ — خودتکرارگری (idempotency)

```json
"idempotency": { "rerun_same_result": true, "resume_on_complete_state_ops": 0,
                 "batch_1_equals_batch_16": true }
```

- اجرای دوباره ⇒ نتیجهٔ یکسان.
- ادامه از حالتِ **کامل** ⇒ **صفر** عملیات (نه تکرارِ کار).
- `batch_size=1` و `batch_size=16` ⇒ نتیجهٔ یکسان ⇒ اندازهٔ batch بر صحت اثر ندارد.

## ۵ — ترتیبِ عملیاتیِ توصیه‌شده برای اجرای واقعی

1. **backup ستون‌های هویتی** (اجباری — بدونِ آن مرحلهٔ ۶ بازگشت‌ناپذیر است).
2. محاسبهٔ کلیدِ سایه‌ای در **یک تراکنشِ فقط-خواندنی**؛ هیچ نوشتنی.
3. تولیدِ دفترِ برخورد و تحویل به مالک برای حل‌وفصلِ دستی.
4. ساختِ ایندکسِ یکتاییِ سایه‌ای با `CREATE INDEX CONCURRENTLY` — بیرونِ تراکنش.
5. dual-read در مسیرِ اسکن/جست‌وجو؛ تصمیم روی کلیدِ قدیمی.
6. بازمحاسبهٔ **batch‌به‌batch** (هر batch یک تراکنش).
7. راستی‌آزمایی: صفر برخوردِ hard، `display` دست‌نخورده.
8. تغییرِ منطقِ مقایسه **در همان انتشار** (ریسکِ اتمی‌بودن).
9. تمرینِ بازگشت روی یک batch، سپس تأییدِ مالک.
